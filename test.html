Final Database Structure (D-Table)

Normalized Relational Schema Design & Business Logic Constraints

Design Implementation Note: The status attribute inside the AVAILABILITY catalog behaves strictly as an administrative operational flag (ACTIVE / DISABLED) to toggle visibility. Temporal expiration (past date/time boundaries) is computed programmatically at the application layer to preserve historical database integrity.

1. USERS

Central repository handling unique identifying attributes for all platform actors (Hosts and Guests).

Column Type Constraint Description
id BIGINT PRIMARY KEY Unique identifier for the user.
name VARCHAR(100) NOT NULL Display name of the user.
email VARCHAR(255) UNIQUE, NOT NULL Unique communication and auth identifier.
timezone VARCHAR(50) NOT NULL User's designated local timezone context.
created_at TIMESTAMP DEFAULT NOW() Audit timestamp of record creation.

2. AVAILABILITY

Stores the recurring weekly baseline availability configurations declared by hosts.

Column Type Constraint Description
id BIGINT PRIMARY KEY Unique availability block ID.
user_id BIGINT FOREIGN KEY → users.id Relates availability config to a specific host.
title VARCHAR(100) NULL Optional labeling for the booking type.
start_date DATE NOT NULL The effective starting date for this schedule.
end_date DATE NULL The boundary limit till when it is valid.
start_time TIME NOT NULL Daily standard working window start time.
end_time TIME NOT NULL Daily standard working window end time.
recurrence_type ENUM NOT NULL NONE / DAILY / WEEKLY
duration_minutes INT NOT NULL Slot length restrictions: 15/30/60/120
status ENUM NOT NULL Administrative toggles: ACTIVE / DISABLED
created_at TIMESTAMP DEFAULT NOW() System timestamp tracking metadata entry.
Functional Mapping Example
User: Mukund (Host) Schedule Schedule: Monday – Friday, 09:00 – 17:00 Granularity: Duration = 30 Minutes Status Flag: ACTIVE Result: System actively synthesizes valid booking slots across the timeline.

3. AVAILABILITY_EXCEPTIONS

Blacklist structure to cleanly isolate specific block-out window dates where bookings are frozen.

Column Type Constraint Description
id BIGINT PRIMARY KEY Unique exception block identifier.
availability_id BIGINT FOREIGN KEY → availability.id Cascades back to the target schedule map.
exception_date DATE NOT NULL The specific calendar date to override to dark.
reason VARCHAR(255) NULL Contextual info (e.g., "Vacation Leave").
created_at TIMESTAMP DEFAULT NOW() Creation audit timestamp.
Exception Mapping Example
Target Date: 12 June Context: "Annual Leave / Public Vacation" Result: No slots generated for this date, despite parent availability rules.

4. BOOKINGS

Main transaction log mapping out concrete, confirmed appointment sessions.

Column Type Constraint Description
id BIGINT PRIMARY KEY Unique meeting receipt tracking handle.
availability_id BIGINT FOREIGN KEY → availability.id Links appointment directly back to source profile.
host_user_id BIGINT FOREIGN KEY → users.id Explicit linkage mapping the provider entity.
guest_user_id BIGINT FOREIGN KEY → users.id (NULL) Optional link if user holds a platform account.
guest_name VARCHAR(100) NULL Fallback descriptor string for external clients.
guest_email VARCHAR(255) NULL Fallback communication node for external clients.
booking_date DATE NOT NULL The target date allocated for this reservation.
start_time TIME NOT NULL Appointment start wall time.
end_time TIME NOT NULL Appointment conclusion wall time.
status ENUM NOT NULL State mutations: BOOKED / CANCELLED
created_at TIMESTAMP DEFAULT NOW() Timestamp logging the generation event.

5. BOOKING_HISTORY (Audit Log Component)

Provides critical audit capabilities, tracking full historical state transitions of a booking for administrative verification.

Column Type Constraint / Permitted Values
id BIGINT PRIMARY KEY
booking_id BIGINT FOREIGN KEY → bookings.id
action VARCHAR(50) String state tracking logs: CREATED, CANCELLED
action_time TIMESTAMP DEFAULT NOW()

Structural Entity-Relationship Layout

USERS [Parent Actor Catalog] | +----(1:N)----> AVAILABILITY [Host Rules Base] | | | +----(1:N)----> AVAILABILITY_EXCEPTIONS [Calendar Exceptions] | +----(1:N [Host Context])----> BOOKINGS [Core Transaction Matrix] | ^ +----(1:N [Guest Context])------+ | +----(1:N)----> BOOKING_HISTORY [Audit Trail]

System Slot Handling Architectural Logic

To avoid massive data duplication and synchronization issues, time slots are dynamic vectors and are never statically stored inside the database. Instead, they are generated purely in-memory by application layer math loops using the parameters provided in the database.

Example Allocation Matrix:
Availability configuration: 09:00–11:00, Interval: 30 minutes.
The backend code splits this window into internal runtime segments: 09:00–09:30, 09:30–10:00, 10:00–10:30, and 10:30–11:00.

Filter Rules: If any synthesized slot has a slot_datetime < current_datetime, or overlaps an entry in the Exceptions table, the UI automatically filters it out without requiring database alterations or state updates.
